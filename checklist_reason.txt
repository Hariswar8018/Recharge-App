1. EXECUTIVE SUMMARY: THE PRIMARY REPORTED ISSUE
--------------------------------------------------------------------------------
CLIENT COMPLAINT:
"The issue is very simple: the ID has NOT been activated, but the system is still
showing the status as 'Activated/Active.' That is the exact problem. Please check
why an unactivated ID is being displayed as Activated and fix the status
synchronization/activation logic."
"My ID is not being generated correctly, and the ID activation is also not
happening correctly."

ROOT CAUSE VERIFICATION:
The unactivated ID is NOT actually activated in the backend database (the database
correctly stores status = 'PENDING'). However, multiple UI layers and fallbacks in
BOTH the Mobile App and the Web Admin Panel are hardcoded or defaulting to
"ACTIVE" / "Active Account" / green verified checkmarks, completely misleading the
user and client into believing the account was activated.

Furthermore, there is a fundamental ID format mismatch (SRD vs SRM vs Mobile Number),
and the 126-member single-leg business plan income calculation requested in
final_checklist.txt is NOT implemented in the backend.

SECTION A: WHY UNACTIVATED IDs SHOW AS "ACTIVATED / ACTIVE"
--------------------------------------------------------------------------------
1. Mobile App Initial State Default:
   - File: `mobile_app/lib/screens/navigation/home_screen.dart` (Line 37)
   - Code: `String _status = "ACTIVE";`
   - Reason: When the app boots or home screen loads, the status variable is
     hardcoded to initialize as "ACTIVE". Before API data is fetched, it renders
     "Status: ACTIVE".

2. Mobile App Null/Fallback Masking:
   - File: `mobile_app/lib/screens/navigation/home_screen.dart` (Line 120)
   - Code: `_status = user['status'] ?? "ACTIVE";`
   - Reason: If the user object is empty, partially loaded, or if the profile API
     fails/times out, the app forces the status to "ACTIVE".

3. Mobile App Drawer & Header Badge Hardcoded Green Verified:
   - File: `mobile_app/lib/screens/navigation/home_screen.dart` (Lines 487-505)
   - Code:
       Icon(Icons.verified, color: Colors.greenAccent, size: 14)
       Text("Status: $_status", ...)
   - Reason: Even if status is "PENDING", it shows a bright green "verified"
     checkmark icon next to it, making it look visually verified/activated.

4. Mobile App Direct Team List Fallback:
   - File: `mobile_app/lib/screens/profile/direct_team_screen.dart` (Line 100)
   - Code: `final status = (member['status'] ?? 'ACTIVE').toString().toUpperCase();`
   - Reason: In direct downlines, any unactivated referral with a missing/null
     status is automatically displayed with a green "ACTIVE" pill.

5. Web Admin Panel Drawer Hardcoded:
   - File: `web_app/src/components/admin/UserProfileDrawer.vue` (Line 13)
   - Code: `<span class="badge-status-active">Active Account</span>`
   - Reason: HARDCODED STATIC HTML. It does not bind to `user.status`. Every single
     user opened in the admin side drawer is shown as "Active Account".

6. Web Admin Panel Add Funds Modal Hardcoded:
   - File: `web_app/src/components/admin/AddFundsModal.vue` (Line 17)
   - Code: `<span class="badge-status-active">Active</span>`
   - Reason: HARDCODED STATIC HTML. Every user is displayed as "Active".

7. Web Admin Panel Teams Tree Tab Hardcoded Fallback & Green Badge:
   - File: `web_app/src/components/admin/TeamsTreeTab.vue` (Lines 109-111)
   - Code:
       <span style="background: #dcfce7; color: #15803d; ...">
         {{ (member.status || 'ACTIVE').toUpperCase() }}
       </span>
   - Reason: Falls back to 'ACTIVE', and uses hardcoded green styling (#dcfce7)
     for all members regardless of status.

8. Web Admin Panel User Management Table Missing Status:
   - File: `web_app/src/components/admin/UserManagementTab.vue` (Lines 65-105)
   - Reason: The registered members table in admin panel DOES NOT EVEN HAVE A
     STATUS COLUMN! An admin viewing the table cannot see whether a user is
     PENDING, ACTIVE, or BLOCKED.

9. Web Admin Filter Fallback:
   - File: `web_app/src/views/AdminDashboard.vue` (Line 766)
   - Code: `list = list.filter(u => (u.status || 'ACTIVE').toUpperCase() === ...);`
   - Reason: Missing statuses are forced into the ACTIVE filter.

10. Profile Cache Retention:
   - File: `backend/routes/user.routes.js` (Line 35-40)
   - Code: `const cacheKey = 'user_profile_' + req.user.id;`
   - Reason: Profile data is cached in Redis/memory. When status updates occur in
     certain flows, the cache is not systematically invalidated, causing stale
     status to be served.

SECTION B: ID GENERATION & MAPPING ISSUES
--------------------------------------------------------------------------------
CLIENT COMPLAINT:
"My ID is not being generated correctly...
1. ID Generation
→ User registers successfully
→ User ID must be generated correctly and uniquely
→ Sponsor ID must be correctly mapped to the sponsor’s mobile number
→ All required user data must be saved correctly in the backend."

ROOT CAUSES FOUND:
1. Identifier Mismatch Across System (SRD vs SRM vs Numeric ID vs Mobile):
   - In Database Registration (`backend/routes/auth.routes.js` line 101):
     Backend generates: `user_code` = `SRM` + 7 random digits (e.g., `SRM4691187`).
   - In Database Primary Key:
     User ID is auto-increment integer `id` (e.g., `8`).
   - In Mobile Home Screen (`home_screen.dart` line 889):
     App generates: `formattedId = "SRD" + _userId.toString().padLeft(8, '0')`
     (e.g., `SRD00000008`).
   - In Registration Welcome Email (`auth.routes.js` lines 120-121):
     Email claims: "Your Sponsor ID / User Code is: SRM4691187, Mobile Number /
     User ID is: 9988494936".
   - CONFLICT: The system generates an SRM code, displays an SRD code on screen,
     uses Mobile Number for login, and uses numeric ID for database relationships!

2. Lookup Endpoint Does NOT Support "SRD" Prefix:
   - File: `backend/routes/user.routes.js` (Lines 185-197)
   - In `router.get('/by-id/:id')`:
     The code strips: `EARNFARMX7AQ96SD`, `EARNFARM`, `EARNKARO97US77`, `SRM`,
     `SRSPO`, but DOES NOT STRIP `SRD`!
   - Result: When a user enters the exact ID displayed on their home screen
     (`SRD00000008`) into the ID subscription screen, `parseInt('SRD00000008', 10)`
     evaluates to `NaN`. The query `WHERE id = NaN` returns 404 User Not Found!
     This directly causes the client's complaint: "My ID is not being generated
     correctly, and the ID activation is also not happening correctly."

3. User Never Sees Generated ID Upon Registration:
   - File: `mobile_app/lib/screens/auth/register_screen.dart` (Line 383)
   - Code: `_successMessage = "Account created successfully! Redirecting to login...";`
   - Reason: Registration immediately redirects to login without showing the user
     their generated User ID or SRM Code.

4. Database Schema Inconsistency in `initDb()`:
   - File: `backend/db.js` (Lines 145-168)
   - `user_code` was not in the original `CREATE TABLE users` query. It was added
     as an `ALTER TABLE` in line 350. On local SQLite or older MySQL databases,
     `user_code` can be NULL (as verified: Admin user id=9 has `user_code = NULL`).

SECTION C: ACTIVATION FLOW ISSUES
--------------------------------------------------------------------------------
CLIENT COMPLAINT:
"2. Activation
→ User makes the required activation payment
→ Payment must be verified successfully
→ Only after successful verification, the account should become Active
→ Activation must be recorded correctly in the backend."

ROOT CAUSES FOUND:
1. Disconnected Fund Deposit vs ID Activation:
   - Currently, adding funds (₹1,200) via Fund Request (`/api/fund/request`) and
     approving it in Admin (`/api/admin/fund-requests/:id/process`) ONLY adds
     balance to `fund_wallet_balance`.
   - It DOES NOT activate the ID!
   - The user must perform a SECOND manual step by going to
     `id_subscription_screen.dart` and submitting `/api/cycles/activate`.
   - Because the UI was already displaying "ACTIVE" prior to this, users and admins
     assumed the ID was already activated, leaving it unactivated in backend.

2. Fallback Vulnerability in `/api/cycles/activate`:
   - File: `backend/routes/cycles.routes.js` (Lines 24-31)
   - Code:
       let targetUser = user;
       if (mobile) {
         const targetRows = await query('SELECT * FROM users WHERE mobileNumber = ? OR id = ?', [mobile, mobile]);
         if (targetRows.length > 0) targetUser = targetRows[0];
       }
   - Reason: If `targetRows` is empty (e.g., mobile number not found or ID
     unrecognized due to SRD prefix), `targetUser` silently remains `user`
     (the caller), activating the caller instead of returning a 404 error!

3. Incomplete Cache Invalidation in Activation:
   - File: `backend/routes/cycles.routes.js` (Line 168)
   - Code: `await invalidateCache('user_profile_' + targetUser.id);`
   - Reason: If User A activates User B from User A's fund wallet, User A's
     profile cache is NOT invalidated. User A still sees their old balance!

SECTION D: TEAM GENERATION & LEVEL STRUCTURE ISSUES
--------------------------------------------------------------------------------
CLIENT COMPLAINT:
"3. Team Generation
→ Once the ID is successfully activated, the system must automatically place
  that ID under the correct Sponsor/Single-Leg structure
→ The team hierarchy must be generated according to the configured levels and
  placement rules (2 -> 4 -> 8 -> 16 -> 32 -> 64 = 126 MEMBERS)
→ Direct team and level-wise team counts must update correctly
→ The same member must not be duplicated or placed incorrectly."

ROOT CAUSES FOUND:
1. Unactivated IDs Enter Team Lists Immediately:
   - File: `backend/routes/user.routes.js` (Line 126)
   - Query: `SELECT ... FROM users u WHERE u.sponsor_id = ? ORDER BY u.id DESC`
   - File: `backend/routes/admin.routes.js` (Line 414)
   - Query: `SELECT ... FROM users u WHERE u.role NOT IN ("admin"...)`
   - Reason: The team endpoints DO NOT filter by `status = 'ACTIVE'`. As soon as
     a user registers with `status = 'PENDING'`, they are already listed in the
     sponsor's team and the admin team tree. Unactivated users are not isolated!

2. 6-Level Hierarchy (2 -> 4 -> 8 -> 16 -> 32 -> 64) is NOT Implemented:
   - The database only has `sponsor_id` (direct referral) and `single_leg_queue`
     (a flat FIFO queue of cycle_id and user_id).
   - There is NO table, schema, or algorithm tracking the 6-level single-leg tree:
     Level 1: 2 members
     Level 2: 4 members
     Level 3: 8 members
     Level 4: 16 members
     Level 5: 32 members
     Level 6: 64 members
     Total: 126 members
   - There is NO level-wise count calculation (e.g. how many members user has in
     Level 1, Level 2, ..., Level 6).

SECTION E: INCOME GENERATION & BUSINESS PLAN WORKFLOW ISSUES
--------------------------------------------------------------------------------
CLIENT COMPLAINT:
"SINGLE LEG 6 LEVEL BUSINESS PLAN BACKEND INCOME WORK FLOW ONLY:
For every successful ₹1,200 Join:
₹300 → Direct Sponsor Income
₹600 → Single Leg 6-Level Pool
₹300 → Company Maintenance
Total = ₹1,200

126-Member Team Income Distribution from ₹75,600 Level Pool:
Top User (1 User)        : ₹12,600
Next Level (2 Users)     : ₹6,200 each (Total ₹12,400)
Next Level (4 Users)     : ₹3,000 each (Total ₹12,000)
Next Level (8 Users)     : ₹1,400 each (Total ₹11,200)
Next Level (16 Users)    : ₹600 each   (Total ₹9,600)
Next Level (32 Users)    : ₹200 each   (Total ₹6,400)
Bottom Level (64 Users)  : ₹0
Total Level Income Paid  : ₹64,200
Level Pool Surplus       : ₹11,400 (Company)
Company Maintenance      : ₹37,800 (Company)
Total Company Amount     : ₹49,200
Total User Income        : ₹1,02,000
Total Collection         : ₹1,51,200"

ROOT CAUSES FOUND:
1. Current Code Uses an Outdated / Completely Different Ladder:
   - File: `backend/routes/cycles.routes.js` (Lines 102-156)
   - Current Code:
     - When members reach 2: pays ₹300
     - When members reach 6: pays ₹400
     - When members reach 14: pays ₹800
     - When members reach 30: pays ₹1,600
     - When members reach 62: pays ₹3,200
     - When members reach 126: pays ₹6,400
     - Total paid = ₹12,700 to ONE user only!
   - Defect: The required plan distributes ₹64,200 across 63 users in the 126-member
     structure (1 gets ₹12,600; 2 get ₹6,200; 4 get ₹3,000; 8 get ₹1,400;
     16 get ₹600; 32 get ₹200). The current code does NOT do this.

2. Company Maintenance (₹300 per join / ₹37,800 per cycle) is NEVER Tracked:
   - Current Code: There is no deduction, ledger entry, or company wallet for the
     ₹300 company maintenance fee per ₹1,200 join.

3. Level Pool Surplus (₹11,400 per cycle) is NEVER Tracked:
   - Current Code: The surplus ₹11,400 from the ₹75,600 pool is neither calculated
     nor credited to the company account.

4. Dependency Enforcement Broken:
   - Client Requirement: ID Generation → Activation → Team Generation → Income Generation.
   - Current State: Since unactivated accounts are displayed as active and enter
     team views without payment verification, the pipeline integrity is broken.

ITEM 1: ID ACTIVATION ISSUE (IDs 22 & 23 AUTOMATICALLY SHOWING AS ACTIVATED)
--------------------------------------------------------------------------------
* Problem Reported:
  "When I am trying to activate the ID, 22 and 23 IDs were automatically showing
   as already activated. I create ids only but I not activate those IDs manually.
   Please check why these IDs showing as activated."

* Root Cause:
  In backend/routes/user.routes.js (GET /by-id/:id), the lookup query used:
    `WHERE mobileNumber = ? OR mobileNumber = ? OR mobileNumber LIKE ? OR id = ?`
  passing `[%${last10}]`. When looking up ID "22" or "23", `last10` was "22" or "23".
  The loose SQL clause `mobileNumber LIKE '%22'` matched any registered user
  whose mobile number ended with 22 or 23 (such as active master/admin accounts).
  Because that matched user was already ACTIVE, id_subscription_screen.dart received
  `status: ACTIVE` and reported: "This mobile number (ID) is already activated."

* Fixation Done:
  1. Completely removed loose `mobileNumber LIKE ?` pattern matching from
     backend/routes/user.routes.js and backend/routes/cycles.routes.js.
  2. Structured lookup into exact criteria:
     - 10-digit numbers: strictly search `WHERE mobileNumber = ? OR user_code = ?`.
     - Numeric short IDs (< 10 digits): strictly search `WHERE id = ? OR user_code = ?`.
     - Non-numeric strings: search `WHERE user_code = ? OR email = ?`.
  3. Attached real-time cycle metadata (`has_active_cycle`, `is_topup_eligible`,
     `active_cycle_id`) to the lookup response.
  4. Updated mobile_app/lib/screens/recharge/id_subscription_screen.dart to
     properly recognize registered pending IDs without false positive activation warnings.

* Current Status:
  RESOLVED & VERIFIED. IDs 22 and 23 look up their own records accurately and
  can be activated manually as intended.

6. 2×2 AUTO-FILL SPILLOVER MATRIX IMPLEMENTATION (6 LEVELS, 126 MEMBERS)
================================================================================
* Problem Reported by Client (SR DIGITAL SEVA®):
  "In a 2×2 Auto-Fill Spillover Matrix, each ID can have only two direct child IDs
   (Left and Right). The next IDs automatically fill the available positions level
   by level up to 6 levels (126 positions). Income must be calculated according to
   my predefined income table and the matrix levels, not by counting every ID below
   an ID as in Single Leg. Please check IDs 3, 4, 5, and 6. Each should generate ₹3,000,
   but the system generates ₹6,500 due to automatic level-based payouts. This will
   cause significant future losses. After checking the entire system overnight,
   I decided we need to fix the logic using a 2×2 Auto-Fill Spillover Matrix."

* Root Cause:
  In the single-leg queue architecture, every newly activated ID was placed in a single
  global linear queue. When calculating downline counts, each ID simply counted all IDs
  placed after it in the entire company line. Consequently, IDs 3, 4, 5, and 6 accumulated
  excess downline members from the entire company rather than only their geometric 2×2
  subtrees, causing premature milestone payouts totaling ₹6,500 instead of their exact
  planned ₹3,000.

* Fixation Done:
  1. Database Schema Initialization (backend/db.js):
     - Added `matrix_positions` table:
       * `id` (INT AUTO_INCREMENT PRIMARY KEY)
       * `cycle_id` (INT)
       * `user_id` (INT)
       * `matrix_index` (INT NOT NULL)
       * `parent_cycle_id` (INT NULL)
       * `parent_user_id` (INT NULL)
       * `leg` (ENUM('L', 'R'))
       * `level` (INT)
       * `createdAt` (DATETIME)
     - Preserved backward compatibility with `single_leg_queue`.

  2. Breadth-First Auto-Fill Placement (backend/routes/cycles.routes.js):
     - Sequential matrix index: `myMatrixIndex = MAX(matrix_index) + 1`
     - Parent index: `parentIndex = floor(myMatrixIndex / 2)`
     - Leg assignment: `leg = (myMatrixIndex % 2 === 0) ? 'L' : 'R'`
     - Depth calculation: `depthLevel = floor(log2(myMatrixIndex))`
     - Automatically fills top-to-bottom, left-to-right across all levels (L1: 2, L2: 4, L3: 8, L4: 16, L5: 32, L6: 64).

  3. 6-Level Ancestor Traversal & Exact Level Payout:
     - When any new ID activates with ₹1,200, the system traverses up to 6 matrix uplines.
     - Each active upline receives ₹100 credited directly to their `main_wallet_balance`
       with transaction logged as `"Matrix Level {depth} Income"`.
     - When an upline reaches 126 downlines in their 2×2 matrix tree, their cycle is marked
       `COMPLETED`, dequeued from queue, and the ₹11,400 Company Level Pool Surplus is logged.
     - Re-entry IDs top up with ₹1,200 and receive the next available bottom position in the matrix.

  4. System Reset Integration (backend/routes/admin.routes.js & backend/reset_db_data.js):
